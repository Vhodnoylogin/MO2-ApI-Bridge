# MO2 AI Bridge

Локальный HTTP-мост к работающей Mod Organizer 2 для скриптов и ИИ-агентов.

Это **папка модуля**, а не сам плагин. Плагин — вложенная папка `plugin_mo2aibridge\`.
Разделение не косметическое: в MO2 уезжает ровно то, что ей нужно, и ни строки проверок.
Проверки модуля лежат здесь же, рядом с ним: в корне репозитория их быть не может — там не
видно, что они проверяют.

**Три уровня раскладки называются по-разному намеренно**, чтобы не читались как одна вложенность:

| Имя | Что это | Где существует |
|---|---|---|
| `wt-mo2aibridge\` | копия ветки на диске | только на диске; git его не знает |
| `mo2aibridge\` | папка модуля | в ветке |
| `plugin_mo2aibridge\` | данные плагина | в модуле |

Имя, под которым плагин известен MO2, — `mo2aibridge`, и оно задано **строкой** `PLUGIN_ID`
в `__init__.py`, а не выведено из имени папки. Из него же берутся имена файла токена и лога.

```
mo2aibridge\                папка модуля
├── README.md              этот файл
├── plugin_mo2aibridge\     ПЛАГИН — только он попадает в MO2
│   ├── __init__.py       фабрика, mobase импортируется лениво
│   ├── plugin.py         жизненный цикл плагина MO2
│   ├── routes.py         таблица «путь → операция»
│   ├── services.py       операции над сборкой, знает mobase
│   ├── runtime.py        главный поток Qt, сокеты, JSON, токен
│   ├── winapi.py         окна и процессы Windows
│   ├── i18n.py           строки и переводы
│   ├── README.md         документация плагина, ru
│   └── README.en.md      документация плагина, en
└── tests\                ПРОВЕРКИ модуля — в MO2 не уезжают
    ├── common.py         где плагин, как до него достучаться, как отчитаться
    ├── run.py            прогнать все наборы подряд
    ├── test_busy_logic.py    юнит: логика занятости без MO2
    ├── test_routes.py        приёмка: все 24 маршрута
    ├── test_plugins_txt.py   приёмка: состояние плагина доезжает до файла
    ├── test_install_modes.py  приёмка: установка, слияние и замена на песочнице
    ├── test_busy_live.py     приёмка: замок на запущенной программе
    └── README.md         что каждый набор проверяет и что уже поймал
```

## Установка

MO2 загружает плагин из `<MO2>\plugins\<папка с __init__.py>` и **берёт имя пакета из имени
этой папки**. Поэтому папка в `plugins\` обязана называться `mo2aibridge`, хотя в репозитории
она зовётся `plugin_mo2aibridge`:

```
xcopy /E /I plugin_mo2aibridge "<MO2>\plugins\mo2aibridge"
```

В разработке удобнее связь: правки видны сразу и без копирования, а имя связи и даёт MO2 нужное
имя пакета.

```
mklink /J "<MO2>\plugins\mo2aibridge" "<папка модуля>\plugin_mo2aibridge"
```

**Для выкладки это значит одно:** в архиве папка должна называться `mo2aibridge`, а не так, как
в репозитории. Скопировать репозиторий целиком и получить работающий плагин нельзя — Python
импортирует пакет по имени папки, и из `plugin_mo2aibridge` получился бы пакет с этим же именем,
а MO2 ищет `mo2aibridge`.

Документация самого плагина — `plugin_mo2aibridge\README.md` и `README.en.md`. Она лежит внутри
пакета намеренно: замок на необратимых операциях возвращает путь к этому файлу, значит файл
обязан приехать вместе с плагином.

## Проверки

```
python tests/run.py
```

Юнит-набор идёт без MO2. Три приёмочных требуют запущенного менеджера и пропускаются с внятным
словом, если его нет; пропуск не считается сбоем. Подробности — `tests\README.md`.

Проверки не импортируются плагином и не видны MO2: они лежат вне пакета и находят его сами —
по соседней папке с `__init__.py`, а не по совпадению имён.

## Что не версионируется

Токен и лог создаются при каждом запуске MO2 рядом с плагином, `__pycache__` — при каждом
импорте. Всё это в `.gitignore`.
