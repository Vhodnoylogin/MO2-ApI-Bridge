# MO2 ApI Bridge

**Локальный HTTP-мост к работающей Mod Organizer 2 для скриптов и ИИ-агентов.**

Всё, что даёт `mobase` — список модов, слитая виртуальная `Data`, порядок загрузки плагинов,
установка мода, запуск утилит внутри VFS — доступно только изнутри процесса MO2. Плагин выносит
эти вызовы на `127.0.0.1`, и тогда ими могут пользоваться скрипты, командная строка и ИИ-агенты,
не кликая по окну менеджера.

Слушает только петлю. Каждый запрос требует заголовок `X-Token`; токен MO2 создаёт заново при
каждом запуске и кладёт в `mo2aibridge-token.txt` рядом с плагином.

*English documentation: [README.ru.md](README.ru.md).*

---

## Два решения, которые важнее кода

**Потоки.** `mobase` и Qt живут в главном потоке. HTTP-сервер крутится в своём, и звать
`IOrganizer` оттуда напрямую нельзя — MO2 упадёт не сразу и непонятно где. Поэтому каждый запрос
заворачивается в задание, отдаётся сигналом в главный поток и ждёт результата. Медленнее, зато
безопасно. Побочное следствие: на долгих операциях окно MO2 замирает — это не зависание.

**Окна.** Мост умеет нажимать кнопки в окнах запущенных утилит, но не вслепую. `/windows`
возвращает заголовок окна и подписи **всех** его кнопок, и только потом `/window` нажимает кнопку
**по её тексту**. Слепого «жми OK» здесь нет намеренно: в диалоге DynDOLOD лежит выбор
параметров, и случайное нажатие тихо испортит результат.

## Установка

Положить папку `mo2aibridge` в `<MO2>\plugins\` и перезапустить MO2. Плагин появится в
**Настройки → Плагины → Tool → MO2 ApI Bridge** и в меню инструментов.

| Настройка | По умолчанию | Смысл |
|---|---|---|
| `enabled` | вкл. | поднимать мост вместе с MO2 |
| `port` | 8930 | порт на `127.0.0.1` |
| `language` | `auto` | язык сообщений: `auto`, `ru`, `en` |

Пункт меню показывает адрес и состояние, а если автозапуск не сработал — поднимает мост вручную
и показывает настоящую причину отказа. Там же кнопка **«Опустить мост»**: настройка `enabled`
читается только при запуске MO2, и снять галочку на ходу мало — а закрыть мост, не выходя из
менеджера, иногда нужно. При выходе из MO2 мост закрывается сам и убирает за собой файл токена.
Диагностика пишется в `mo2aibridge.log` рядом с плагином: загрузка, старт, полная трассировка
при любой ошибке.

**Два экземпляра MO2 одновременно** — обычное дело: Skyrim и Fallout держат открытыми оба.
Второй мост не может встать на тот же порт, поэтому берёт следующий свободный (до десяти
подряд) и пишет токен в файл с этим портом в имени — `mo2aibridge-token-8931.txt`. У кого
экземпляр один, у того имя файла прежнее, `mo2aibridge-token.txt`. То есть клиенту достаточно
посмотреть, какие файлы токена лежат рядом с плагином: имя называет порт.

**Что нужно снаружи.** MO2 2.5 с включённой поддержкой Python-плагинов — больше ничего, кроме
одного случая: маршруту `/install` нужен установленный **7-Zip** (`7z.exe` ищется в
`Program Files\7-Zip` и в `PATH`). Стоит в другом месте — впиши путь в ключ `sevenZip`
файла `mo2aibridge-config.json`, он создаётся рядом с плагином при первом запуске.
Остальные маршруты работают без 7-Zip.

**Только Windows.** Мост опирается на `user32` и `kernel32` напрямую: перечисление процессов,
состояние окон, Корзина. На других системах MO2 Python-плагины загружает, но эти вызовы
работать не будут.

## Маршруты

Токен подставляется обёрткой; ниже он опущен для краткости.

### Чтение (GET)

| Маршрут | Параметры | Отдаёт |
|---|---|---|
| `/ping` | — | профиль, игра, версия MO2, пути к `mods`, `overwrite`, `downloads`, и `busy` — занята ли MO2 запущенной программой |
| `/api` | — | что на самом деле умеет `IOrganizer`, `IModList`, `IPluginList`, `IProfile` в этой сборке MO2 |
| `/mods` | — | все моды: имя, активность, признак обязательного, приоритет |
| `/mod` | `name` | полная карточка мода, см. ниже |
| `/analyze` | `name`, `conflicts`, `limit` | разбор мода одним вызовом: карточка, файлы, плагины, кто с кем спорит |
| `/profiles` | — | все профили инстанса и активный |
| `/plugins` | — | порядок загрузки, активность, мастера, esl-флаг, признак «нет записей», мод-источник |
| `/vfs` | `path`, `filter` | файлы виртуальной `Data` по маске |
| `/origins` | `path` | все моды-поставщики файла, **первый побеждает** |
| `/resolve` | `path` | виртуальный путь → настоящий файл на диске |
| `/dirs` | `path` | подкаталоги виртуальной `Data` |
| `/procs` | — | что мост запускал за сессию: `alive` у каждой записи, `running` — сколько живо; плюс что MO2 считает активным |
| `/windows` | `pid` или `key` | окна процесса и подписи их кнопок |
| `/updates` | `mod` (можно несколько) или `all`, `offset`, `limit`, `timeout` | обновления по живому Nexus: вердикт по файлам и датам, версии не сравниваются |

### Действия (POST)

| Маршрут | Тело | Что делает |
|---|---|---|
| `/refresh` | — | перечитать `mods\` и профиль |
| `/install` | `archive`, `name`, `paths`, `mode` | установка без диалогов; `mode` — `merge` или `replace`, когда папка занята. `replace` **необратим** и требует ключ, см. ниже |
| `/toggle` | `mod`, `active` | включить или выключить мод |
| `/plugins/state` | `set`, `apply` | включить или выключить плагины пачкой |
| `/plugins/order` | `order`, `apply` | задать порядок загрузки целиком |
| `/vfsexport` | `outDir`, `timeout`, `legacyWalk` | выгрузка всей виртуальной `Data` в CSV |
| `/run` | `binary`, `args`, `cwd`, `wait` | запуск утилиты **внутри VFS**; **необратимо**, см. ниже |
| `/window` | `hwnd`, `action`, `button` | `close` или `click` по подписи кнопки |
| `/mods/priority` | `mod`, `priority` | **необратимо**, см. ниже |
| `/mods/rename` | `mod`, `newName` | **необратимо** |
| `/mods/remove` | `mod`, `withArchive` | **необратимо**; ответ содержит карточку мода до сноса |

Неизвестный путь возвращает 404 и обе таблицы отдельно — половина ошибок в том, что чтение
послано как POST, и наоборот.

### Коды ответа

| Код | Поле `code` | Что это значит |
|---|---|---|
| 200 | — | сделано; отказ замка тоже приходит с 200 и полями `applied: false`, `reason` |
| 400 | `badRequest` | **ошибка в запросе**: нет обязательного поля, чужой режим, неизвестный мод, негодное булево. Текст в `error`, трассировки нет |
| 403 | — | нет или не тот `X-Token` |
| 404 | — | такого пути нет; в ответе обе таблицы маршрутов |
| 500 | `bridgeFailure` | **поломка моста**: неожиданное исключение. В `trace` последние 800 знаков |

Разница между 400 и 500 существенна: первое значит «спроси иначе», второе — «мост сломался,
повторять бессмысленно». Раньше и то, и другое выходило пятисоткой, и отличить их было нельзя.

Отказ замка — занятости или необратимого — это **не ошибка**: приходит 200, а в теле
`applied: false` и `reason` со значением `busy` или `danger`. Так сделано нарочно: замок
сработал штатно, и клиент должен разбирать тело, а не ловить исключение.

## Мост выполняет, помнит вызывающий

Плагин **ничего не запоминает между вызовами** и ничего не решает за вызывающего. Никакого
журнала отката внутри нет, и появиться он не должен: решать, куда возвращать мод, — дело того,
кто отдал команду, а не того, кто её выполнил.

Отсюда обязанность, которая заменяет память: **ответ на изменяющую операцию содержит всё,
чем её можно обратить**. Не намёк, не «было изменено», а готовые данные.

| Маршрут | Чем обращается | Что для этого в ответе |
|---|---|---|
| `/toggle` | обратным включением | `was` — состояние до правки, и `changed` |
| `/mods/priority` | возвратом приоритета | `from` и `to` |
| `/plugins/state` | обратной установкой | `changes` со `from`/`to` по каждому плагину |
| `/plugins/order` | восстановлением порядка | `before` — **весь** прежний порядок |
| `/mods/rename` | обратным переименованием | `fromPath`, `toPath` и `nexusId` |
| `/install` | удалением созданной папки | `path` и `created` |
| `/mods/remove` | переустановкой из архива | `card` — карточка мода, снятая **до** сноса |

Где обращение выражается одним запросом, ответ содержит его целиком — поле `undo` с готовыми
`route` и `body`. Это подсказка, а не обещание: мост не проверяет, что с тех пор ничего не
изменилось, и не хранит её. Захочет вызывающий откатить — отправит; не захочет — забудет.

**Подпись карточки.** У каждого ответа на изменяющий маршрут есть `op` — имя операции
(`toggle`, `install`, `refresh`, `pluginState`, `pluginOrder`, `run`, `priority`, `rename`,
`remove`) — и `applied`. У любого отказа вдобавок `reason`: `busy`, если MO2 занята запущенной
программой, и `danger`, если не передан ключ необратимого. Прежние ключи остаются на месте:
форма ответа меняется только добавлением, иначе тихо ломаются чужие вызовы.

**Карточка удаления** отдаётся и при отказе тоже, то есть посмотреть, что именно потеряется,
можно не удаляя: имя, версия, `nexusId`, ссылка, из какого архива мод собран и лежит ли этот
архив на диске, приоритет, включённость, число файлов, категории и заметки.

**Всю работу мост делает сам.** Вызывающий отдаёт команду и получает, что было и что стало;
распаковка, копирование, удаление и уборка — на мосту. Там, где он удаляет файлы своими руками,
они уходят **в Корзину**, а не мимо: это его собственное решение, а не забота вызывающего.

**Архив по умолчанию остаётся.** `/mods/remove` сносит папку мода, но не трогает загрузку
в `downloads\` — то есть мод восстановим переустановкой. Удалить и архив можно явным
`"withArchive": true`; тогда он тоже уходит в Корзину, и ответ говорит `archiveRecycled`.

## Карточка мода — `/mod?name=…`

Версия, `nexusId`, **готовая ссылка на страницу Nexus**, собственные категории MO2, заметки, из
какого архива поставлен, отклонённая версия обновления, состояние лайка и отслеживания, флаги
`isSeparator`, `isForeign`, `isBackup`, `isOverwrite`.

Три вещи здесь нельзя получить из `meta.ini` вовсе:

| Поле | Почему важно |
|---|---|
| `isSeparator` | иначе разделитель определяется по суффиксу `_separator` в имени папки, то есть по соглашению |
| `categories`, `primaryCategory` | собственные категории и цвет MO2 хранит отдельно от `meta.ini` |
| `ignoredVersion`, `endorsed` | какие обновления пользователь уже отклонил; без этого они предлагаются заново |

Поле `url` собирается из `nexusId`, когда тот известен. Полагаться на `m.url()` нельзя: у части
модов он отдаёт голый домен без `/mods/<id>`, то есть ссылку в никуда. Ответ самой MO2 сохраняется
отдельно как `urlFromMO2`.

## Разбор мода одним вызовом — `/analyze?name=…&conflicts=1&limit=80`

Карточка, путь, число файлов, список плагинов, образец имён и — главное — **кто с кем спорит**:
в каких файлах мод побеждает, а в каких проигрывает, с полным списком поставщиков. В отличие от
расчёта по стороннему индексу, это реальный порядок активного профиля.

`conflicts=0` отключает самую дорогую часть: спор проверяется вызовом `getFileOrigins` на каждый
файл мода, и на моде в тысячи файлов это заметно.

## Обновления — `/updates`

Единственная точка, где сборка спрашивает Nexus, есть ли файл новее. Мост ходит в Nexus сам,
через `IOrganizer.createNexusBridge()` — тем же путём и тем же ключом API, что и MO2, — и сам
выносит решение. Чаты и скрипты ничего не сравнивают и никуда не ходят: они запрашивают у моста
и получают факты вместе с вердиктом. Помнить результат — дело индекса сборки: `tools\updates-sync.py`
проходит все моды через этот маршрут и пишет вердикты в `index.db`, откуда их отдаёт `idx.py updates`.

```
GET /updates?mod=<имя>&mod=<имя>          выбранные моды
GET /updates?all=1&offset=0&limit=50      вся сборка страницами; в ответе total и more
```

Правила решения перенесены из прежнего разборщика страниц и теперь живут только здесь:

- **Номера версий не сравниваются никогда.** Их печатает автор руками, и они расходятся между
  шапкой страницы, строкой файла и `meta.ini`. Решают два факта: какие файлы страницы мы
  скачивали — по `fileID` из `.meta` рядом с архивом в `downloads\` — и в каком разделе каждый
  файл лежит сейчас. Скачанный файл, уехавший в Old files, устарел по определению; скачанный
  файл в живом разделе актуален, пока страница не предлагает файл новее той же роли.
- **Роль** — имя файла без версии и без шума, но со всем остальным: JContainers SE и
  JContainers VR остаются разными ролями и не выдают себя за обновления друг друга. Сборка под
  GOG — не обновление к сборке под Steam, тело UNP — не обновление к CBBE.
- **Сомнение трактуется как «есть обновление»**: всё, что не сошлось уверенно, попадает
  в `CANNOT-MATCH`, а не молча объявляется актуальным.

Вердикты — те же слова, что в индексе: `UPDATE-AVAILABLE`, `UP-TO-DATE`, `CANNOT-MATCH`,
`REUPLOADED` (наш файл со страницы исчез, а Main новее), `DOWNLOADED-NOT-INSTALLED` (свежий архив
уже в `downloads\`, а мод собран из старого), `NO-NEXUS-ID`, `ERROR`. Каждая запись несёт `why`
словами, `installed` (архив, `fileId`, дата), `downloaded` (архивы этой страницы на диске),
`newest`, `items` по ролям с `newer` и `extra` — файлы Main/Update другой роли.

Пауза между запросами и таймаут — в настройках (`updates.delaySec`, `updates.timeoutSec`):
у API Nexus дневной лимит, и полный проход по сборке в несколько сотен модов должен в него
укладываться. Чтение работает и при занятой MO2. В ответе `via` говорит, каким путём спрошен
Nexus, `quota` — сколько запросов осталось по лимиту.

**Раздел Nexus берётся у самой MO2** — `gameNexusName()` знает его для любой игры, которую
менеджер умеет вести. Таблица `nexusDomains` в настройках — только перекрытие для случаев
вроде Skyrim VR, у которого своего раздела на Nexus нет и моды берутся из раздела SSE.
Слепого умолчания нет намеренно: подставив чужой раздел, мост получал бы страницу **другого**
мода с тем же номером и выносил по ней уверенный вердикт. Не выяснили раздел — `ERROR`
со словами, а не догадка.

**Отказ канала прекращает обход.** Отказ одной страницы (404, битый ответ) — это строка
в ответе рядом с остальными. Но негодный ключ (401, 403), исчерпанный лимит (429) и
оборванная связь означают, что провалится и каждый следующий запрос: на сборке в полторы
тысячи модов это полторы тысячи бессмысленных обращений, а на 429 — ещё и продление запрета
каждым из них. Поэтому обход останавливается, а в ответе появляются:

| Поле | Что означает |
|---|---|
| `stopped` | почему обход прекращён; пусто, если дошёл до конца |
| `unchecked` | сколько модов осталось неспрошенными |

Обход останавливается и **пока в суточной квоте ещё остаётся запас** (`updates.quotaReserve`,
по умолчанию 50). Ключ здесь общий с самой MO2: доев его до нуля, мост оставил бы человека
и без обновлений, и без загрузок в менеджере — а причину тот искал бы где угодно, только
не в плагине. Обрыв связи считается по числу отказов подряд (`updates.netFailsBeforeStop`,
по умолчанию 5): одна неудача бывает у кого угодно, пять подряд означают, что канал лёг.

**Два пути к Nexus, и выбирается один на сессию.** Первый — мост самой MO2,
`createNexusBridge()`. В MO2 2.5.2 он из Python не работает: ответ `filesAvailable` несёт
`QList<ModRepositoryFileInfo*>`, и PyQt отказывает на подписке. Тогда плагин берёт ключ API
из хранилища учётных данных Windows — запись `ModOrganizer2_APIKEY`, куда его кладёт сама MO2
при подключении к Nexus, — и спрашивает `api.nexusmods.com` напрямую. Ключ живёт только в
памяти плагина, наружу не отдаётся ни одним маршрутом и в лог не пишется. Нет записи — ответ
`ERROR` со словами, что MO2 не подключена к Nexus.

## Установка мода без закрытия MO2

MO2 держит списки в памяти и перезаписывает файлы профиля при работе — потому правки состава
традиционно требуют её закрыть. Это ограничение снимается полностью.

**Штатный путь — `POST /install`:**

```json
{"archive": "D:\\...\\downloads\\SomeMod-1.2.7z",
 "name": "Some Mod",
 "paths": ["00 Core", "10 Textures 2K"]}
```

Мод заводится через `createMod`, архив распаковывается самим мостом, и в папку кладутся ровно
указанные подпапки; `fomod\` и корневой `meta.ini` пропускаются. Ответ говорит, сколько файлов
скопировано и был ли пропущен `fomod`.

`installMod` намеренно не используется: он запускает установщик MO2, а тот **всегда** спрашивает
имя, при совпадении имён спрашивает «заменить или слить», а на архиве с `fomod/ModuleConfig.xml`
открывает мастера. Автоматизировать эти окна нельзя — MO2 на Qt, нативных кнопок у неё нет. Для
FOMOD ручной путь и так единственный верный: варианты разбираются чтением `ModuleConfig.xml`,
а не кликами.

Если мод с таким именем уже есть, маршрут отказывает. Слияния и замены не бывает: изменённый файл
кладётся **отдельным модом**, перекрывающим исходный.

### Папка уже занята: слияние или замена

Установщик MO2 в этом случае спрашивает диалогом; мост спрашивает полем `mode`, и без него
**отказывает** — молча писать поверх чужой работы нельзя.

| `mode` | Что делает | Нужен ключ | Что теряется |
|---|---|---|---|
| не указан | отказ с объяснением | нет | ничего |
| `merge` | кладёт выбранное поверх прежнего | нет | перекрытые файлы; их список в ответе |
| `replace` | сперва убирает прежнее содержимое **в Корзину**, потом кладёт выбранное | **да** | ничего безвозвратно |

`replace` — единственный режим, который теряет чужую работу, и потому он закрыт тем же
ключом `iUnderstandTheRisk`, что и удаление (см. «Необратимые операции»). Обычная установка
и слияние ключа не требуют.

`meta.ini` при замене не трогается: он принадлежит MO2 и хранит `nexusId`, категорию и имя
архива — то есть опознание мода помимо имени папки.

**Имя мода обязано быть именем папки** — без разделителей пути, без двоеточия, не `.` и не
`..`. Иначе отказ 400. Это не придирка: имя подставляется в путь внутри `mods\`, а на Windows
склейка пути отбрасывает первую часть, если вторая абсолютная, — и `replace` с именем вроде
`C:\Users\<кто>\Documents` унёс бы в Корзину чужую папку.

Порядок работы: сначала распаковка, потом чистка. Так задумано — распаковка заодно проверяет,
есть ли на машине 7-Zip и цел ли архив. При обратном порядке машина без 7-Zip получала бы
папку мода в Корзине и никакой установки взамен.

Ответ в обоих случаях говорит, что было и что стало: `filesBefore`, `filesAfter`, `added`
и `addedCount`, `overwritten` и `overwrittenCount`, `removedToRecycleBin`. Списки обрезаются
на двухстах именах, счётчики — нет.

**Ручной путь**, когда файлы уже разложены:

1. распаковать мод в `mods\<Имя>` мимо MO2, записать `meta.ini`;
2. `POST /refresh` — MO2 подхватывает новую папку и заводит мод в списке;
3. `POST /toggle` — включить;
4. `POST /mods/priority` — поставить на нужное место.

Проверено: папка создана вручную, `/mods` её не видел; после `/refresh` мод появился с
приоритетом 1006; `/toggle` включил его, и `modlist.txt` на диске обновился с `-` на `+`.
Удаление папки плюс `/refresh` убрало строку из профиля.

**Следствие для чтения:** пока MO2 запущена, `modlist.txt` на диске может отставать от памяти на
несколько секунд. Живое состояние спрашивать у `/mods`, а не у файла.

## Необратимые операции

Маршруты `/mods/priority`, `/mods/rename`, `/mods/remove` меняют сборку необратимо: перестановка
приоритета меняет порядок перекрытия файлов во всей сборке, переименование ломает строки в
профилях, ссылающиеся на мод по имени папки, а удаление сносит папку **с диска**, а не строку
в профиле.

`/install` с `"mode": "replace"` стоит там же: он уносит прежнее содержимое мода в Корзину,
то есть теряет чужую работу. Установка без режима и `"mode": "merge"` ключа не требуют —
они ничего не теряют.

`/run` стоит в том же ряду, и выше всех: под MO2 поднимается чужой процесс с виртуальной
`Data`, и что он сделает со сборкой — перепишет вывод генератора, соберёт патч, снесёт кеш, —
мост не контролирует и обратить не сможет. Поэтому запуск закрыт и замком занятости, и ключом.

Поэтому они не работают, пока в теле запроса нет поля:

```json
"iUnderstandTheRisk": "yes-I-read-the-docs-and-accept-irreversible-changes"
```

Без него маршрут **ничего не делает**, а возвращает объяснение, что именно он бы сделал, и путь
к этому файлу. Смысл не в секретности значения, а в том, чтобы агент, случайно дёрнувший такой
маршрут, не мог ничего испортить: узнать значение можно только прочитав этот раздел, то есть
вместе с описанием последствий.

Записи в `/plugins/state` и `/plugins/order` устроены мягче — там достаточно `"apply": true`,
потому что порядок загрузки восстанавливается запуском LOOT, а удалённый мод — нет.
`/plugins/order` вдобавок требует **полный** список и отказывается работать, если в нём чего-то
не хватает или есть лишнее.

## Когда запущена игра

Пока через MO2 работает программа — игра, DynDOLOD, TexGen, что угодно — менеджер занят ею,
и **ни один изменяющий маршрут не срабатывает**. Отказ выглядит так же, как у замка на
необратимом: `applied: false`, плюс `busy: true` и карточка запущенного процесса.

```json
{"applied": false, "busy": true,
 "running": {"app": "SkyrimVR.exe", "pids": [23456], "isGame": true, "viaMO2": true},
 "blocked": "включение или выключение мода",
 "why": "Сейчас работает SkyrimVR.exe, и MO2 занята ею. ..."}
```

Причина не в вежливости к окну MO2, а в устройстве USVFS. Виртуальная `Data` уже смонтирована
в процесс игры. Переставить мод, включить плагин или перечитать списки на ходу — значит развести
две картины мира: игра продолжает видеть прежнюю сборку, а файлы на диске описывают новую. Дальше
это всплывает не сразу и не там, где сделано: сохранения ссылаются на плагины в старом порядке,
а `refresh` под работающим USVFS способен уронить и саму MO2.

Отказывают: `/refresh`, `/install`, `/toggle`, `/run`, `/plugins/state` и `/plugins/order`
**с** `apply`, и вся необратимая тройка `/mods/priority`, `/mods/rename`, `/mods/remove`.

Работают по-прежнему **все** маршруты чтения — `/mods`, `/plugins`, `/vfs`, `/origins`,
`/resolve`, `/analyze` и остальные, — а также предпросмотр `/plugins/state` и `/plugins/order`
без `apply`: он ничего не меняет. Разбирать сборку во время игры можно целиком, нельзя только
её править. Работают и `/windows` с `/window`: ими закрывают диалог самой запущенной утилиты,
то есть именно они и снимают занятость.

Проверено на живой MO2 дважды. На утилите: `/mods` вернул полный список, все девять
изменяющих маршрутов отказали. На настоящей игре, запущенной кнопкой в окне MO2, — шесть минут
игры под USVFS, и всё это время чтение отвечало **мгновенно**: профили, 97 плагинов, файлы
виртуальной `Data`, поставщики файла. Диалог блокировки MO2 не останавливает её событийный
цикл, поэтому задания из потока сервера продолжают выполняться.

**Игра ловится не обратным вызовом, а перечислением процессов, и это не запас, а необходимость.**
MO2 запускает Skyrim VR через `sksevr_loader.exe`; загрузчик стартует `SkyrimVR.exe` и тут же
завершается. Имя, о котором сообщил `onAboutToRun`, к живому процессу уже не относится — искать
надо исполняемый файл игры. Поэтому `viaMO2` отвечает на вопрос «MO2 считает запуск активным»,
а что именно она стартовала, видно в `mo2Run`.

**Как это узнаётся.** Двумя способами сразу, потому что по отдельности каждый врёт:

| Способ | Что видит | Чего не видит |
|---|---|---|
| `onAboutToRun` и `onFinishedRun` | всё, что запускает MO2 — и мостом, и кнопкой в её окне | что запустили её потомки, а не она сама |
| перечисление процессов Windows | жива ли игра и то, о чём MO2 сообщила по имени | процесс, о котором она не сообщала |
| включённость главного окна MO2 | её собственный замок, ровно как его видит человек | ничего, пока окно не выключено |

Занятость объявляется, если сработал **любой** из трёх. Игра, запущенная мимо MO2 — прямо из
Steam, — тоже считается занятостью: менять сборку под работающим Скайримом нельзя независимо
от того, кто его запустил.

**Учёт запусков не «лечится» проверкой процессов, и это принципиально.** Соблазн есть: запись
осталась, процесса с таким именем в системе нет — похоже на мусор, хочется стереть. Но MO2
сообщает о завершении сама, и пока она этого не сделала, её замок держится. Значит запись — не
мусор, а единственная оставшаяся улика.

Так и вышло на практике. Плагин `Envoy` поднял изнутри игры голосовую службу `pythonw.exe`;
игра закончилась, служба осталась жить в задании MO2, и менеджер честно показывал «заблокирован,
пока приложение запущено». А мост, «вылечив» учёт, отвечал `busy: null` — защита отключалась
ровно в том случае, ради которого писалась. Теперь такое состояние видно полем `heldByUnknown`:
запуск не закрыт, а знакомых процессов нет, то есть замок держит тот, о ком MO2 не говорила.

**Свой запуск и чужой учитываются по-разному, потому что MO2 сообщает о завершении не про
всё.** О завершении она говорит только про то, чего ждала сама, — то есть про запуск кнопкой в
её окне. Программу, поднятую мостом через `startApplication`, она не ждёт, и `onFinishedRun` по
ней не приходит вовсе: запись висела бы вечно, а мост считал бы себя занятым до перезапуска
менеджера. Поэтому свои запуски мост снимает с учёта сам, как только процесс умер, — про них он
знает правду и без MO2. Чужие держатся до её слова: именно в них вся защита.

Обратная опасность — застрявшая запись, если сообщение о завершении потеряется совсем. Маршрута
для сброса нет намеренно: иначе замок обходился бы одним запросом. Сбросить учёт может только
человек и только руками: пункт **Tools → MO2 ApI Bridge** показывает, что MO2 считает
активным, и предлагает сброс.

Обхода у этого замка нет намеренно, в отличие от замка на необратимом. Там ключ подтверждает
осознанный выбор, а здесь выбирать нечего: закрыть программу — единственный способ.

## Подводные камни, найденные на практике

**`/run` принимает зарегистрированное имя утилиты, а не путь.** `startApplication` с полным путём
к `.exe` молча не создаёт процесс: RootBuilder отрабатывает, а окна не появляется. С именем из
списка исполняемых файлов MO2 (`TexGen`, `DynDOLOD`, `PGPatcher`) всё работает сразу.

**`waitForApplication` останавливает не только MO2, но и мост.** Вызов уходит в C++ и не
отпускает GIL, а интерпретатор у плагинов один на всех — вместе с главным потоком встаёт и поток
HTTP-сервера. Наблюдалось буквально: пока работала запущенная утилита, мост не отвечал даже на
`/ping`, и ожил в ту же секунду, когда она закрылась. Поэтому `/run` с `"wait": true` ждёт сам,
через `WaitForSingleObject` на дескрипторе процесса: ctypes на время вызова GIL отпускает, и
занят остаётся только поток одного этого запроса.

**Окна самой MO2 читать бесполезно.** MO2 написана на Qt, все её виджеты нарисованы внутри
одного `HWND`, нативных дочерних окон у них нет. Пустой список кнопок для окна класса `Qt*`
означает «не вижу», а не «кнопок нет». Механизм годится для утилит на WinAPI — таких, как
диалоги DynDOLOD и TexGen, — и не годится для самой MO2. Такие окна помечены `qtWindow: true`.

**`/procs` копится всю сессию и сам не чистится.** Запись о запуске кладётся при вызове
`/run` и остаётся до закрытия MO2: о завершении СВОИХ запусков менеджер не сообщает, ждать его
слова тут нечего. Поэтому у каждой записи спрашивается система — поле `alive`, а `running`
говорит, сколько живо на самом деле. Без этого три давно закрытых утилиты из проверок выглядели
как три работающие программы.

**`/plugins/state` дописывает `plugins.txt` сам, и это не украшательство.** `setState` меняет
список в памяти MO2, а файл она переписывает в свои моменты — обычно при выходе. Игра стартует
именно с файла, и любой `/refresh` между правкой и выходом читает файл обратно, молча отменяя
правку. Стоило это трёх сорванных прогонов: мост отвечал `applied: true`, а плагин в игре
оставался выключенным. Теперь звёздочка переставляется прямо в существующих строках файла, а
набор строк и их порядок не трогаются вовсе — это дело MO2. Ответ содержит поле `file` с путём
и списком изменённых имён.

Читать файл при этом надо с `newline=''`: в обычном текстовом режиме Python схлопывает `CRLF`
в `LF`, определение концов строк даёт `LF`, и файл переписывается чужим форматом. Поймано ровно
так — первая же запись сменила все 96 строк.

**`/vfsexport` берёт дерево у самой MO2.** `IOrganizer.virtualFileTree()` отдаёт готовую слитую
`Data`. Прежний способ — собрать корень из деревьев отдельных модов и дальше идти вширь через
`listDirectories` — остался запасным (`"legacyWalk": true`) и появился только потому, что
`listDirectories('')` и `('.')` отдают пусто и корень казался недостижимым. В ответе поле `how`
говорит, каким из двух способов получена выгрузка: они дают разное число путей.

**Поле `archive` всегда пустое**, пока в настройках MO2 выключен разбор архивов
(`archive_parsing_experimental=false`, значение по умолчанию). Содержимое BSA в виртуальное
дерево при этом не попадает вовсе.

**Ответ зависит от активного профиля.** `/origins` на файл из категории, которой нет в текущем
профиле, вернёт пусто — это правда о профиле, а не потеря данных.

## Перевод

Все видимые пользователю строки лежат в `i18n.py`, отдельно от логики. Чтобы добавить язык:
скопировать словарь `EN`, перевести правые части, левые не трогать, дописать язык в `LANGS` и
выбрать его настройкой `language`. Ключи — короткие латинские метки, а не английские фразы:
фраза меняется при вычитке, и тогда все переводы разом отвязались бы от кода.

Непереведённый ключ ничего не ломает: берётся английский, а если нет и его — сама метка.

## Настройки

Порт и язык задаются в окне настроек плагина MO2. Остальное — таймауты главного потока по видам
работы, длина списков в ответах, где искать `7z.exe`, домены Nexus по имени игры — лежит в
`mo2aibridge-config.json` рядом с плагином. Файл создаётся при первом запуске из встроенных
умолчаний; чего в нём нет, берётся из умолчаний, так что старый файл переживает добавление
новых ключей. Испорченный файл не роняет мост: в лог пишется причина, работа идёт по умолчаниям.

Путей к конкретной машине в умолчаниях нет: кандидаты на `7z.exe` складываются из переменных
окружения `ProgramFiles` и `ProgramFiles(x86)` и дополняются поиском по `PATH`.

## Раскладка

| Файл | Слой | Знает про |
|---|---|---|
| `winapi.py` | операционная система | окна и кнопки; ничего про MO2 и сеть |
| `runtime.py` | транспорт | главный поток Qt, сокеты, JSON, токен |
| `services.py` | предметный, фасад | собирает области и отдаёт маршрутам их методы под прежними именами |
| `base.py` | предметный | контекст областей, общий приём изменения, подпись карточки |
| `busy.py` | предметный | занятость MO2: учёт запусков и три источника замка |
| `reading.py` | предметный | чтение состояния и виртуальной Data |
| `install.py` | предметный | установка мода: свежая, слияние, замена |
| `mods.py` | предметный | включить, выключить, перечитать; приоритет, имя, удаление |
| `loadorder.py` | предметный | состояние и порядок плагинов, запись `plugins.txt` |
| `launch.py` | предметный | запуск программ и их окна |
| `updates.py` | предметный | обновления по живому Nexus: запрос через MO2 и правила решения |
| `routes.py` | маршрутизация | какой путь во что отображается, и больше ничего |
| `plugin.py` | жизненный цикл | интерфейс плагина MO2 |
| `config.py` | настройки | таймауты, лимиты, где искать 7-Zip; поперёк всех слоёв |
| `i18n.py` | строки | поперёк всех слоёв |

Предметный слой разобран по областям, и ни одна из них не знает про HTTP. Все области получают
один `Context` — `IOrganizer`, способ попасть в главный поток, куда писать след, настройки — и
общий замок занятости `BusyGuard`. Изменяющие маршруты идут одним приёмом `Domain.change`:
отказать, если MO2 занята → проверить входные данные → выполнить в главном потоке → подписать
карточку. `Services` — тонкий фасад: те же 25 методов, те же имена, и атрибуты учёта
(`launched`, `game_exe`, `procs`) на прежних местах, потому что на них стоят проверки.

В `__init__.py` намеренно лежит только фабрика, а `mobase` импортируется лениво: иначе
`from mo2aibridge import i18n` требовал бы запущенной MO2, и нижние слои нельзя было бы проверить
по отдельности.

## Безопасность

Сервер привязан к `127.0.0.1` и не слушает внешние адреса. Токен случайный, 32 символа,
пересоздаётся при каждом запуске MO2 — то есть перехваченный токен живёт не дольше сессии.
Сравнивается он за постоянное время, чтобы не подбирался по времени ответа.

Мост даёт полный доступ к сборке: включение и выключение модов, изменение порядка загрузки,
запуск программ. Это ровно те же права, что у любой программы, запущенной пользователем, но
через сеть петли. Держать его включённым имеет смысл тогда, когда им кто-то пользуется.
